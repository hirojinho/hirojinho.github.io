Designing an app to be operated by an AI agent

Notes from marginalia, a self-hosted study tutor where an AI agent is a first-class operator — and the architecture decisions that made that load-bearing instead of a demo.

Eduardo Haraguchi / June 2026 / 16 min read

The thesis

Most “AI features” are a chat box wired to a few function-call tools, sitting beside an app designed for a human with a mouse. The agent is a guest. It reaches a thin, second-class slice of what the app can do, through an interface invented for it and then maintained grudgingly.

marginalia takes the opposite stance: I wanted agent-operability to be a real design axis, equal to the human UI, shaping the architecture from the data layer up. The app is a self-hosted study tutor: a single Go binary with an embedded single-page frontend, SQLite for all state, RAG over a local course corpus, and an LLM tutor that reads your slides, tracks a study plan, and takes notes with you. The tutor isn’t the interesting part. The architecture around it is, specifically the decisions that make “an agent operates this app” load-bearing instead of a demo.

One thing shapes everything else, so I’ll say it plainly. I’m an AI-infrastructure engineer, not a career Go programmer. My Go is thin. I built much of marginalia by directing coding agents rather than hand-writing idiomatic Go, and that turned out to be the point rather than an embarrassing footnote: I used coding agents to build software meant to be operated by agents. Designing for an agent operator and being driven by one are the same skill from two ends. The discipline I leaned on wasn’t Go fluency. It was deciding what the operations are, where the boundaries sit, and what the agent is and isn’t allowed to touch, then making an agent execute against that. More on that later.

A word on scale. This is single-developer, personal-use software that runs on a home server and gets used daily for real study. It is not a multi-tenant SaaS. Some decisions below are right because the blast radius is one person and one box, and I’ll say so where it matters. The claim isn’t that this is production-grade at scale. It’s that designing for an agent operator forced a cleaner architecture than I’d have written for a human alone.

Why agent-operability is a real axis

Decide that an agent should operate your app, not just answer questions about it but change its state, and you hit a question most apps never ask: what is the real surface of operations, and who can reach it? In a human-only app that answer is implicit and scattered across HTTP handlers and frontend JavaScript, shaped however the UI needed it. That works until a non-human operator shows up needing the same operations in a form it can script. Then you bolt on an API exposing a narrower, subtly inconsistent slice, and now you have two code paths and two sets of bugs to keep in sync. The API rots because it’s nobody’s primary path.

Agent-operability is a forcing function for an old discipline: separate the operation from the caller. Do that well and the agent isn’t a special case. It’s another caller of the same operations the human uses.

The design: one implementation, three doors

The core structural decision in marginalia is that every domain operation is a single method on one type, agent.App, reached through three doors:

  1. The web UI, over HTTP. handler/*.go calls App methods directly.
  2. A token-gated HTTP/JSON API. The same handlers, gated by a bearer token, so an external agent can reach the operations the browser reaches.
  3. claw-cli, a command-line binary the in-sandbox agent drives, whose subcommands call the same App methods the handlers call.

This is verifiable in the code, not aspirational. App.LoadPlan, App.SavePlan, and App.UpdateSessionTopic each have one body and multiple front doors. LoadPlan is called by the HTTP handler (handler/plan.go) and by claw-cli‘s plan show subcommand (claw-cli/main.go). UpdateSessionTopic is reached by the chat handler, the sessions handler, and claw-cli session topic. Both the HTTP server and the CLI construct the same *agent.App from the same environment and the same SQLite file, the CLI via newAppFromEnv() in claw-cli/main.go. There is no separate “agent service” with its own logic; the agent calls the identical methods the browser does.

A deliberate non-decision reinforces this: there is no service/repository layer (ADR 0002). The original stability plan prescribed SessionService/PDFService and a mockable repository/ layer, the standard testable-backend advice. I skipped it. agent.App methods are the persistence-and- orchestration surface; handlers and claw-cli call them directly; tests use in-memory SQLite instead of mock interfaces. Two layers (agent/, handler/) instead of four. The ADR records the honest tradeoff: the concrete SQLite dependency leaks slightly into App signatures, and handler tests need real DB fixtures rather than mocks (cheap with :memory: SQLite, but it would hurt at higher LOC or with team contributors). At one developer and ~5,500 LOC, fewer layers to keep in sync was the right call. “One implementation, three doors” is easier to hold true when there’s only one implementation to begin with.

claw-cli is what makes the agent a real operator rather than a chatbot. It’s a scriptable command surface built for a non-human: plan show/status/toggle/rewrite, pdf list/current/extract, rag search, memory save/search/load, course settings get/set, knowledge create/show/search/list, confidence log/trajectory, note save, session topic, web fetch, skill dispatch, component emit/show. Each subcommand is a thin wrapper over an App method or a Tool* function in agent/tools_*.go, with no business logic of its own.

The agent’s context is rendered from the database, per turn

A chatbot gets a static system prompt. An operator needs to know the live state of the thing it’s operating. So before each agentic turn, marginalia synthesizes a fresh AGENTS.md briefing from the current database state. agent/sandbox.go creates a per-session sandbox directory at <vault>/data/agent-sessions/<sessionID>/ and, in Create(), calls writeAgentsMD(), which shells out to claw-cli memory load. That invokes AssembleAgentsMD() in agent/memory.go, which reads live state and renders it into one markdown document. The sections it assembles, each pulled from the DB at request time:

  • the learner’s profile (Memory rows with kind='profile'),
  • global observations and interests and per-course context (kind='project', scoped by course_id),
  • active feedback rules (kind='feedback'),
  • the recent sessions digest for the active course,
  • the skills index, parsed from the SKILL.md frontmatter of the mounted skills,
  • plus pedagogy rules and memory-tool instructions.

There’s real restraint here, not just string concatenation. AssembleAgentsMD enforces a per-section byte cap and a total ~4 KB ceiling, dropping lower-priority sections on overflow. The briefing is bounded on purpose, because context is a budget.

What I care about most is liveness. Because AGENTS.md is regenerated every turn from the source-of-truth tables, a change anywhere (a setting written through the settings form, a plan toggled in the rail, a fact saved to memory) is visible to the agent on its next turn, with no restart and no cache to invalidate. ADR 0016 leans on exactly this. When the tutor changes a course setting via claw-cli course settings set, the write lands in the course_settings table and “takes effect on the next turn for free” because the briefing is rebuilt from that table. Human and agent read and write the same state through the same doors, and the per-turn briefing is how the agent re-orients to it.

The runtime: an embedded Pi subprocess, streamed as SSE

The earliest /chat was an in-process Go loop calling an OpenAI-compatible endpoint with a fixed list of function tools. That’s the common shape, and it has a ceiling: the model can’t run protocols, follow skills, accumulate memory, or dispatch multi-step work. ADR 0006 records replacing it. The gap between this app and my day-to-day Claude Code workflow was the runtime fabric (skills, memory, verification), not the LLM. The fix was to embed an agent runtime rather than write a smarter prompt.

So marginalia embeds Pi (@earendil-works/pi-coding-agent, MIT) as the runtime. agent/pi_runner.go‘s RunPi() spawns pi --mode rpc as a subprocess, working directory set to the per-session sandbox, a --skill flag pointing at the mounted skills. In RPC mode the subprocess stays alive across prompts; a turn’s message is sent as JSON over stdin. Pi emits a JSONL event stream on stdout, which parsePiLine() decodes into typed events: token (text deltas), reasoning (thinking deltas), tool_start and tool_end, skill_start, and done (with token-usage counts). Because the agent invokes claw-cli through Pi’s bash tool, every domain operation surfaces as a tool_start/tool_end pair.

handler/chat.go translates that stream into Server-Sent Events. streamPiTurn() reads PiEvent values off a channel and handlePiEvent() writes and flushes one SSE frame per event: {"delta": "..."} for tokens, an input summary for tool_start, an output summary for tool_end, usage counts on done. The browser renders tokens, a collapsible “thinking” block, and a tool panel from those frames.

The costs are in the ADR. Per-turn latency rose to roughly 5–15 seconds (Pi cold-start plus streaming), accepted because per-turn isolation is the right v1 default. The deploy gained a third binary, pi alongside marginalia and cloudflared, which softens ADR 0003’s “single binary” stance to a footnote. And the real capability ceiling: non-Claude OpenCode models (DeepSeek, Kimi, GLM) are weaker on protocol-heavy skills, so the app doesn’t pretend to replace every Claude Code interaction. The choice was explicitly reversible. A Node sidecar or a TypeScript extension remain available if Pi-over-RPC proves too brittle for the model fleet. I’d rather ship a reversible v1 with named limits than a “general agent” that quietly fails on the hard skills.

RAG over the local corpus

The retrieval layer is small and reads cleanly. agent/chunker.go‘s ChunkFile() splits course markdown by heading structure (H1 parent, H2 sections), infers course id and category from the file path, and splits over-long sections (>1500 bytes) on paragraph boundaries. agent/embed.go‘s EmbedBatch() POSTs to an OpenAI-compatible /embeddings endpoint and returns [][]float32. agent/vectorstore.go‘s IndexCorpus(), kicked off in a goroutine at startup per main.go, walks data/corpus/, re-embeds only files that changed (NeedsReindex()), and stores each chunk’s vector as a little-endian float BLOB in a corpus_chunks table in the same SQLite DB. Search() embeds the query, scans the candidate rows, computes cosine similarity in Go, filters below a 0.3 threshold, and falls back to keyword search when embedding fails or returns nothing.

This is a brute-force cosine scan, not an ANN index. No HNSW, no vector extension. For a personal corpus that’s the right amount of machinery: a few readable functions in the one SQLite file everything else lives in, with no operational dependency to break. The agent reaches all of this through one door, claw-cli rag search, the same retrieval the rest of the app uses.

The overnight spec→verify pipeline, with the verifier as a hard gate

The most ambitious piece of agent-operability isn’t inside a study session. It’s the pipeline that lets an agent change the app itself, unattended, overnight. I author a feature spec as a markdown file and push it; overnight, a Pi runtime on a separate machine implements the change, verifies it, and on success deploys it.

The design is a trust gradient. Pi’s model output is the least-trusted layer; below it sit an author-written bash verifier, an orchestrator shell script, the scheduler, and finally systemd/git. Every load-bearing decision pushes risk outward, from the model toward determinism. The architecture lives mostly in shell scripts on the VPS, out of this repo by design. The contract it enforces is in-repo, and that’s what I’ll walk through.

That contract is the verifier as a hard gate, documented in specs/README.md and checked by scripts/lint-specs.sh. Every spec must carry a ## Verification recipe with two bash blocks. The ### Pre-baseline block must fail on current main: exit non-zero means “the feature is genuinely missing, as expected.” If it exits zero (spec already satisfied, or verifier broken), the run aborts to failed/. After implementation, the ### Post-acceptance block, usually the same script, must pass against a staging instance built from the new binary. Exit codes are the only judgment that crosses the model/deterministic boundary — not the model’s self-report, not a diff review. The gate runner spins staging on a separate port against a snapshot of the prod DB, runs pre-baseline against the old binary and post-acceptance against the new one, and only a clean exit-0 lets the change merge --ff-only and deploy. The same deterministic- tool discipline shows up one level down, inside the app: ADR 0017 records why plan edits go through ToolRewritePlan, a deterministic rewrite that preserves task UUIDs across edits (matching by title) so a live session’s confidence and retrieval history stays anchored to its task rather than orphaned.

This is TDD’s red-green discipline turned into an unattended pipeline’s safety mechanism. The author’s pre-baseline-must-fail step is the red test. If you can’t write a check that fails before and passes after, you don’t have a spec the agent can be trusted to execute. The directory itself is the state machine: queue/ → in-progress/ → done/ | failed/.

The orchestrator scripts — scheduler, staging spin-up, deploy, rollback — live in a private infra repo, not here. What’s in this repo, and described above, is the spec contract the pipeline enforces: the verifier-as-gate, the pre-baseline-must-fail red step, and the directory state machine.

What I learned directing agents to build this

Orchestrating coding agents to build this changed what the hard part was. It stopped being syntax and became specification. An agent will happily write plausible Go that drifts from what you meant, so the leverage moved upstream into the ADRs, the claw-cli command contract, and the spec/verifier discipline. Those documents are how I steer a coding agent. They’re also how the in-app agent reads the system. The same artifacts serve both. The overnight pipeline is the sharpest case: the verifier exists because I don’t trust agent output on its own, mine or the app’s, and the only way I found to delegate real work safely was to make a dumb deterministic check the final authority. Working this way taught me to treat my Go thinness as a design constraint, not a wall. If I can’t easily read every line, the architecture has to stay legible, the boundaries explicit, the gates automatic. That pressure produced better structure than confidence in my own code would have.

The engineering judgment: boring on purpose

The substrate under all of this is dull, and the ADRs say why. No Docker (ADR 0003): deploy is GOOS=linux go build, scp, atomic binary swap, systemctl --user restart, rollback a literal file swap (mv marginalia.bak marginalia). One host, no fleet. Docker would buy reproducibility I get from go.mod/go.sum pinning, at the cost of a daemon and a registry. Vanilla JS, no build step (ADR 0004): plain HTML/JS plus pdf.js, so go build is the entire build. Stay with Go, restructure rather than rewrite (ADR 0001). Push to main, no PRs (ADR 0005), with the explicit note that this breaks the moment a second contributor shows up.

Two things make this judgment defensible rather than just lazy. Every one of these is written down with its tradeoff and its revisit trigger: ADR 0002 revisits “if the codebase doubles or a second backend appears,” ADR 0003 “a second host pushes back toward containers,” ADR 0005 “introduce PRs when a second contributor arrives.” The decisions are scoped to actual constraints, not asserted as universal truths. And the boring substrate is what makes the agentic parts safe. An overnight agent that deploys via binary swap can be rolled back by a human in one mv, and a briefing rendered from SQLite has no cache layer to desync. The adventurous parts sit on a substrate dull enough that recovery is trivial when they misbehave.

There’s also a code-style spine: a STYLE.md with eleven locked rules (one operation per line, typed domain identifiers, interface{} only at protocol boundaries, behavior-named tests against real :memory: SQLite), enforced by .golangci.yml and a pre-commit hook. A full-repo golangci-lint run ./... passes clean, and the config isn’t lenient: it turns on errcheck, revive‘s exported-doc-comment rule, forbidigo (banning interface{} and any outside protocol boundaries), and a dozen others, with the only exclusions being narrow, per-file, and documented inline for the genuine JSON/sql.Scan boundaries where interface{} is legitimate. The pre-commit hook additionally gates newly introduced issues with --new-from-rev HEAD, so the clean baseline stays clean as the agent commits.

What generalizes, and what doesn’t

Pulling back from the study domain, four ideas transfer.

  • Make the operation the unit, and give it more than one door. The agent stops being a second-class integration the moment it calls the same methods the UI calls. Separating operation from caller is good architecture independent of agents; the agent just makes the cost of not doing it immediate.
  • Render the agent’s context from source-of-truth state, per turn. A static prompt describes an app; a briefing assembled from live tables describes this app right now. The payoff is that human and agent writes are symmetric and instantly mutually visible.
  • Put a deterministic gate between the model and anything irreversible. Exit codes, not self-reports: the model suggests a change, and a dumb, trustworthy check decides whether it ships. This is the most reusable idea here, and it has nothing to do with which model you run.
  • Keep the substrate boring so the adventurous parts stay recoverable. Agent autonomy is only as safe as the rollback under it.

Now the limitations, because the design has real edges.

  • Per-turn Pi cold-start is 5–15s of latency. Fine for deep study, wrong for a snappy chat product. Per-turn isolation over a warm long-lived agent is a v1 tradeoff, not a final answer.
  • The capability ceiling is the model fleet, not the harness. Protocol-heavy skills degrade on non-Claude OpenCode models. The app names this rather than papering over it.
  • Almost every “one operation, three doors” guarantee rests on convention, not a compiler. Nothing forces a new App method to gain a claw-cli subcommand — no codegen, test, or lint check enforces door parity. Several ADRs (0016, 0017) exist precisely because a capability was added to the UI/Go layer but not wired to the agent’s door, and had to be retrofitted. The pattern is a discipline, not an invariant.
  • This is one user on one box. The choices that make it elegant (no service layer, no Docker, push to main, brute-force RAG) are scoped to that. I’d make several differently for a team or a tenant.

The claim I’d defend in an interview isn’t “this is how all agent-operated software should be built.” It’s narrower and more useful. Once you decide an agent is a real operator of your app, the cleanest path is to stop building it a special door and make it walk through the same ones your humans do, then put a deterministic gate between it and anything you can’t take back. marginalia is one worked example, tradeoffs written down, built the way it preaches: by an engineer directing agents to make software that agents operate.
